## Presence state machine (final thresholds and behaviour)
- `unknown → arriving` on the first read; `arriving → present` once **`arrive_reads` (3)** reads land within a sliding **`arrive_window_s` (10 s)** → emits **arrived**. An arriving tag whose window empties goes back to `unknown`.
- `present → missing` after **min(60 s, depart_after_s/2)** unseen (informational; no event). A read in `missing` → `present`, no event.
- `missing → departed` after **`depart_after_s` (900 s)** unseen → emits **departed**; the tag is forgotten, and a later read starts a new arrival.
- Door gating (`depart_requires_door_closed`, `continuous` mode only): timer departures only fire while `door_entity` is **closed and has been closed ≥ arrive_window_s**. Door unknown blocks departures. Door state comes from the HA entity (`on` = open, `off` = closed, anything else = unknown).
- Restart: EPCs persisted as `present` are restored as present. Door mode: nothing departs until 2 completed sweeps. Continuous mode: not for one full `depart_after_s`. `arriving` isn't persisted (re-reads redo it).
- Late-landing protection: an add that may have reached Grocy more than once (timeout / 5xx / connection reset, then retried) is re-checked `verify_after` (60 s) later; duplicate stock entries carrying the same op marker are consumed again. Pending checks survive restarts and are counted as `verifying`.
- Q1: an arrival whose cycle equals the link's `skip_add_cycle` journals a *skipped* add (status done, resolution `in_stock`, nothing sent). The departure then journals a normal consume, by amount, with no stock entry id.
- Q3: replaying an add first compares its cycle with the persisted presence: `presence.cycle > op.cycle` or (same cycle and `departed`) → cancel add + consume (resolution `cancelled`).
- Q2: an ambiguous consume with no stock entry id → `failed` + resolution `review`; it can't be blindly retried (Retry is refused). Only **Consume now** (by amount) or **Dismiss** closes it.
- **Door mode (v0.3.0)**: reads from any window (continuous or sweep) feed the same arrival rule. `finish_sweep(completed)` advances the miss count only for completed sweeps; a read anywhere resets it. `tick(accrue=…)` adds to the unseen timer only while the activity is `continuous`, using an exact per-tag mark so idle time is skipped, not averaged. `min_sweeps_before_departure = 2` blocks both sweep and timer departures after a restart.
- Journal rules: an arrival journals one add per (EPC, arrival cycle) in the same SQLite transaction as the presence update (`dedupe_key = epc:cycle:add`). A departure journals a consume only if that cycle's add was journaled and didn't fail. Linking a tag that is already present journals that cycle's add once.

## Linking flow (final topics and payloads)
- `pantry_hub/linking/<station_id>/barcode` ← `{"barcode": "...", "ts": <epoch s>, "in_stock"?: true}` (`station_id` matches `[A-Za-z0-9_-]{1,32}`; the firmware uses `kroger_scanner`)
- `pantry_hub/linking/<station_id>/tag` ← `{"epc": "<hex>", "rssi": -45.2, "ts": ..., "in_stock"?: true}` (`in_stock` on either message marks the new link "already in stock"; the `linked` result message says so)
- `pantry_hub/linking/<station_id>/result` → `{"status": "linked|unknown_barcode|tag_already_linked|timeout|error", "product": "...", "message": "...", "barcode"?: "...", "epc"?: "..."}`
- Flow: by-barcode lookup → else external lookup `?add=true` → else `unknown_barcode` + "needs product" list. The first tag must arrive within **15 s** of the barcode; then tags are collected for **1 s** and the strongest RSSI wins (unknown RSSI loses; ties keep the first). Tags after that window are ignored. Already linked → `tag_already_linked` with the existing product (relink only in the web UI). A new barcode on the same station replaces the session. A tag with no session → `error` "Scan a barcode first".
- Linking never changes Grocy stock.
- `pantry_hub/resync/result` also carries `review_ops: [{op_id, product_id, product, epc, note}]`.
- Also published: `pantry_hub/events` (`{"event_type": "arrived|departed", "epc", "product", "product_id", "linked", "ts"}`), `pantry_hub/state` (retained), `pantry_hub/last_link` (retained), `pantry_hub/resync/result` (retained), `pantry_hub/status` (`online`/`offline`, LWT). Subscribed: `pantry_hub/resync/press`, `pantry_hub/sweep/press`, `homeassistant/status`. The door comes from the HA API, not MQTT.

## Linking station firmware (pins, UARTs, U107 power, mode behaviour, Kroger Restock event/action used)
- Device name **`kroger-scanner`** (reuses the wall scanner, per decision Q3 = b); HA action `esphome.kroger_scanner_feedback` unchanged.
- QRCode2: **G5** RX (base TX → Atom), **G6** TX, **G7** TRIG (unused, auto mode), **G8** LED (driven by M14; unused), UART 115200. U107: Grove **G1** RX / **G2** TX (swap if no reads), UART 115200, 5 V from USB-C. Logs over USB-CDC (`hardware_uart: USB_SERIAL_JTAG`).
- U107 (JRD-4035): TX power **15 dBm** default (`u107_tx_power_dbm`, schema 5–26), region US. Single-poll every 100 ms during a scan; strongest tag after the first tag + 1 s; scan up to 15 s. The module is sent to **sleep** at boot and after every scan, so the radio only transmits during link-mode scans (5 V stays on: a hardware limit).
- Modes: **Kroger** (default, LED off when idle, existing result colours) → barcode calls **`kroger_restock.scan_upc`** with `upc` + **`source: esphome`** (from `ha-kroger-restock` `esphome/kroger-scanner-atoms3.yaml` / `services.yaml`). **Link**: double-click toggles; slow dim blue pulse; auto-exit after 60 s idle; exit shows a 250 ms cyan flash, then LED off. Results: green linked, amber unknown barcode, magenta already linked, red error/timeout.
- Button: double-click = link mode; short press (after ~350 ms) = `kroger_restock.print_list`; hold 1–6 s = `kroger_restock.sync`.
- Beep: switch "Link result beep (unverified)", default off; sends `m14_beep_cmd` (default `21 63 42 01`, the M14 "beep on decode" command) 1/2/3×. Marked unverified.
- **In-stock session (firmware 0.2.0)**: in link mode, scanning the mode card (QR `PANTRY-HUB:IN-STOCK`, case-insensitive) toggles it. Pulse: dim blue (0, 0.2, 1) → dim amber (1, 0.55, 0). Barcode and tag messages carry `"in_stock": true` while it's active. It ends on link-mode exit (double-click, 60 s idle) or a second card scan; card scans count as activity for the idle timer; a scan in Kroger mode is ignored. Entity: `binary_sensor` In-stock session.
- MQTT is used for the linking topics only (`discovery: false`); the native API is kept for Kroger mode.

## Spec changes vs. this spec
v0.4.0: see `pantry-hub/DECISIONS.md`. The main ones: Part 1's polling ships with the new shell (commit 2); `tokens.css` was created here because Laundry Hub v0.2 isn't merged (the copies must stay in sync); Inter isn't downloaded (used if installed); the mockup's brand/size line isn't shown (no such data); no "Grocy not set up yet" banner (the app can't start without Grocy); pictures answer 204 when missing; barcodes-without-product, resync and link-by-barcode kept although not on the mockups; `/settings/door-state` → `/api/door`.

v0.3.4:
- **"Other ports total ≥ 10 reads"** is the other ports' reads summed over the same 5 sweeps (not per sweep).
- **Single port and `present_tags`**: taken at the *start* of each sweep, and the rule needs tags present at the start of any of the 5. With a dead single port every tag departs after `depart_after_missed_sweeps` (2) misses, so `present_tags` is 0 long before the fifth sweep; checking it at evaluation time would never fire.
- **Streak, not a fixed window**: a port's silence is counted as consecutive completed sweeps without a read, and any read from any window (sweep, continuous, even an aborted one) resets it. Otherwise a port that read only during a continuous window would be flagged again on the next sweep.
- **Clearing is immediate**: a flagged port clears on its first tag read as it arrives (via `TagRead.antenna`), not when the window ends, since a continuous window can last `open_continuous_s` (600 s).
- One notification id for all ports (`pantry_hub_dead_port`); its message lists each flagged port on its own line. Added attribute `dead_ports` alongside `per_port_reads_last_sweep`.
- Door mode only (continuous mode has no sweeps).

v0.3.3:
- **aiochainway v0.4.0 not tagged** (then): implemented against v0.3.0's `get_antennas` / `get_power_all` / `set_antennas` / `set_power` behind a small adapter, `pantry_hub/reader_config.py`. Done in v0.3.4: the adapter now calls `UR4Client.ensure_config()` and the local verify code is deleted.
- **"After every reconnect"**: with `per_window` every window is a new connection, so the settings are read (two short commands) before every window; writes still happen only on a difference. With `persistent` they're verified once per connection (initial, after `auto_reconnect`, or after a failure).
- **Save flag**: v0.3.0's `set_antennas` always sends the SDK's save flag; there's no separate parameter. `set_power` has no save flag in the protocol; power is re-checked on every connection anyway.
- **Power read-back** is compared as whole dBm (the reader reports dBm × 100).
- **Door mode only**: continuous mode leaves the reader in its own auto mode and never sends it configuration commands.
- Supersedes v0.1.0 spec change 9 ("the hub never configures the reader"): in door mode it now enforces antennas and power.

v0.3.2:
- **Notification link**: the persistent notification links to the app's ingress panel (`/hassio/ingress/<slug>`, slug derived from the container hostname the Supervisor sets, e.g. `1a2b3c4d-pantry-hub` → `1a2b3c4d_pantry_hub`). HA can't deep-link into a sub-page of an ingress panel, so it opens the status page, which shows a "needs a door sensor" banner with a link to Settings. If the hostname isn't recognised, the message says "Open Pantry Hub's web UI → Settings".
- **Also relaxed**: `depart_requires_door_closed` (continuous mode) no longer requires `door_entity` in the options; the web UI choice counts too. With neither, the door is unknown, so timer departures wait (as before for an unknown door), and the same notification asks for a sensor.
- **No HA token** (local development only; under the Supervisor there always is one): the app starts instead of refusing; the door stays unknown and the picker says the API is unavailable.
- Saving a choice while `door_entity` is set in the options stores it anyway (used once the option is cleared) and says so.
- If the saved entity no longer exists in HA, the picker still shows it, marked "not found in Home Assistant".
- Not changed: the door picker isn't exposed over MQTT; changing it needs the web UI (or the option).

v0.3.1:
- **Probe period**: "every 10 min while idle" is measured from the last contact with the reader (end of a window, or the last probe), so with the door closed and hourly sweeps the probe runs about 5 times between sweeps, and never while sweeps come more often than every 10 min.
- **Persistent mode and failures**: after a window or probe fails, the persistent client is closed and the next window builds a fresh one (`connect(retries=3)`). `auto_reconnect` covers drops between windows; it doesn't revive a sweep that was cut short (aiochainway ends that stream as `connection_lost`, as intended).
- **Continuous (UDP) mode** is unchanged: its optional `reader_tcp_probe` still runs `get_version` every minute.
- **20-min job timeout**: wasn't in `test.yml` yet; added as `timeout-minutes: 20` to both the Pytest matrix and the new macOS repeat job.
- `WindowResult` now also carries `end_reason`, `stop_acknowledged` and `unique_count` from aiochainway's `SweepResult` (logged per sweep).

v0.3.0 door-driven reading:
- **Version**: 0.3.0 (your title), not 0.4.0. 0.3.0 hadn't been released (it held only Q8), so both are in 0.3.0.
- **"Repair issue in HA"**: apps have no API to create Repairs entries (only integrations do). Implemented as a persistent notification with a fixed id (`pantry_hub_door_unavailable`), raised after the door has been unavailable for 120 s and dismissed on recovery, plus `door_unavailable_notified` on `sensor.pantry_hub_reader_activity`.
- **Door source**: `door_entity` is read over the HA API (`homeassistant_api: true`), replacing `door_entity_topic` (MQTT) from 0.1.0. That's a breaking change for 0.1.0 configs; a clear error says so. `depart_requires_door_closed` remains for `continuous` mode.
- **MAC via discover()**: aiochainway's `discover()` is passive (it only listens for the reader's UDP 1111 broadcasts) and no TCP command returns the MAC. With the reader on the IoT VLAN and HA on 192.168.1.38, the broadcasts most likely never reach HA (and Docker bridge networking may also drop them), so the `host:port` fallback is the expected result. The MAC is added as an extra device identifier next to `pantry_hub`, so HA keeps a single device whichever id is used.
- Which door changes abort a window: opening aborts anything; leaving "open" aborts the continuous window; closed ↔ unknown doesn't interrupt a sweep (otherwise the first door report at start would abort the startup sweep).
- Failed sweeps (reader offline) and failed pending close/requested sweeps retry after `retry_s` = 60 s (internal constant) instead of a whole interval; no tight loop.
- "Sweep now" while a sweep is running is ignored; during a continuous window it aborts the window, sweeps, and the continuous window resumes until `open_continuous_s` from opening.
- Added option `reader_tcp_port` (8888). In door mode `binary_sensor.pantry_hub_reader_online` means "the last window reached the reader" (with closed-door sweeps an hour apart, a time-based online check would flap).
- Container smoke test uses `reading_mode: continuous` (CI has no Home Assistant); door mode is covered by the integration tests.

## Hardware/setup impact (ports, firewall, disk, power supply)
- **Ports**: door mode (default) needs no incoming port: HA → reader **TCP 8888**. Continuous mode: UDP **8888** on 192.168.1.38. UDP **1111** mapped for the reader's announcements (MAC). Ingress 8099 internal; no host networking.
- **Firewall**: door mode: allow TCP 192.168.1.38 → reader:8888 (with return traffic). Continuous mode: UDP reader → 192.168.1.38:8888. Station → Mosquitto TCP 1883.
- **Reader provisioning**: work mode **command** (the hub also switches it at start); no UDP destination needed in door mode.
- **Door sensor**: a Home Assistant `binary_sensor` for the pantry door (`on` = open), chosen in the web UI (**Settings**) or set as `door_entity`. Door mode starts without one (v0.3.2) but then only sweeps every `closed_sweep_interval_s` and asks for a sensor.
- **Disk**: free space first (86% full). The image is a small Alpine Python image; the SQLite DB is tiny. State is republished on change, with counters at most once a minute, to keep the recorder small.
- **Grocy app** needs its port enabled and ssl off (or certificates) for `http://a0d7b954-grocy`.
- **Antennas** (v0.3.3): `reader_antennas: [1]` on the bench, `[1, 2]` with both SP11s. Every enabled port must have an antenna connected; Pantry Hub enables exactly these ports on the reader.
- **Power**: linking station needs **5 V ≥ 2 A USB-C** (QRCode2 + U107). Reader conducted power **≤ 27 dBm** (8.3 dBi SP11, FCC 36 dBm EIRP).
- U107 needs mounting beside the scanner, antenna facing out (housing doesn't fit; separate ha-kroger-restock PR later).
